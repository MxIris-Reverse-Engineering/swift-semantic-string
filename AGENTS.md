# AGENTS.md
This file provides guidance to coding agents when working with code in this repository.

## Build & Test Commands

```bash
swift package update && swift build 2>&1 | xcsift
swift package update && swift test 2>&1 | xcsift

# Run a single test (Swift Testing filter syntax)
swift test --filter "SemanticString Tests/Empty initialization" 2>&1 | xcsift
# Or by symbol name
swift test --filter SemanticStringTests 2>&1 | xcsift
```

- Swift tools version: **6.2** — strict concurrency is on, so every public type must be `Sendable`.
- No external dependencies. The only system imports are the platform locking primitives, confined to `Storage/CacheLockStripes.swift`: `os.lock` on Darwin (`Synchronization.Mutex` would require macOS 15, `NSLock` would drag in Foundation), `SRWLOCK` on Windows, `pthread_mutex_t` elsewhere. **Every one is behind `#if canImport`, and nothing else in the target imports anything** — an unguarded `import os.lock` turns a pure-stdlib package into a Darwin-only one, and `Package.swift`'s `platforms:` only sets minimum versions, it does not stop SwiftPM building for Linux.
- Single library target `Semantic` + single test target `SemanticTests` (Swift Testing `@Suite` / `@Test` / `#expect`, not XCTest).
- Deployment targets: macOS 10.15, iOS 13, macCatalyst 13, tvOS 13, watchOS 6, visionOS 1.
- **watchOS means 32-bit, and no simulator build will tell you.** `arm64_32` / `armv7k` are the only 32-bit Apple targets left, so `UInt` is 32 bits there and a 64-bit literal is a hard compile error — one that `-typecheck` does not catch (it fires during code generation) and that the watchOS *simulator* does not catch either, because on Apple silicon the simulator is `arm64`. There is no CI in this repo. Before touching anything with pointer-width-sensitive arithmetic, check it explicitly:
  ```bash
  xcrun --sdk watchos swiftc -swift-version 6 -wmo -O -c \
    -sdk "$(xcrun --sdk watchos --show-sdk-path)" -target arm64_32-apple-watchos6.0 \
    -module-name Semantic -o /dev/null $(find Sources/Semantic -name '*.swift')
  ```

single-flatten, Codable idempotence, scope leaks), `ThirdReviewRegressionTests` (defects the third review turned up, fail-first: hand-built element slots, frozen canonical equality, grapheme-aligned span splitting, enumerateSpans trap coverage via exit tests, decoder span-count bounding, plus pins for the container-emptiness divergence and freezing preserving `isEmpty`), `FourthReviewRegressionTests` (defects the fourth review turned up, fail-first: frozen Codable round-trip idempotence for an out-of-range `identifierIndex` — the decoder must accept what the unchecked `FrozenSemanticStringTests`.
- **A test that passes against a reverted design is not a test.** Assertions that actually depend on the storage design reach into `_storage.atoms` / `_storage.elementEndOffsets` / `elements.representation` and say so; behavior-only tests belong in `StorageDivergenceRegressionTests`, where running them against an older revision is the point. `RedesignRegressionTests` was written before the redesign and verified red (9 of 13) against the code it replaced. When adding a test "for" a storage change, check that it fails without the change.
- **Timing assertions and ThreadSanitizer don't mix.** Under `--sanitize=thread` the full suite reports three `StressTests` budget overruns; add `--no-parallel` and only one survives — the 10k-component Codable round trip (~208 ms against a 200 ms budget), which overruns on `main` too. The other two are CPU contention between tests running in parallel, not regressions. Judge timing from an uninstrumented run.
- **Concurrency tests are worthless uninstrumented.** `ConcurrencyTests` passes with the locking deliberately broken: publishing the string cache without its lock leaves all 17 tests green while ThreadSanitizer reports 82 races. After touching storage, caching, or locking, run `swift test --sanitize=thread --filter ConcurrencyTests` — a clean assertion run proves nothing.

## Architecture

A **semantic string library** for building richly-typed text output (like `NSAttributedString`, but the attribute *is* a semantic role rather than a visual style). Originally designed for representing code declarations in reverse engineering tools. Follows a SwiftUI-like component/builder pattern.

### Core Type Hierarchy

**Protocol chain:** `SemanticStringComponent` (like `View`) → `AtomicSemanticComponent` (leaf nodes with `string` + `type`).

**Key types:**
- `SemanticString` (`Sources/Semantic/SemanticString.swift`) — the main **builder** container. Copy-on-write via an internal `Storage` class (`@unchecked Sendable`) holding a **flat atom array plus an element boundary table** (see below) and a lazy `String` cache. Mutations go through `makeUniqueForMutation()`. Conforms to `Codable` (encodes as `[AtomicComponent]`), `Hashable`, `ExpressibleByStringLiteral`, `TextOutputStream`, and itself `SemanticStringComponent`.
- `FrozenSemanticString` (`Sources/Semantic/Frozen/FrozenSemanticString.swift`) — the immutable **terminal form**, produced one-way by `SemanticString.frozen()`. Stores `text: String` (full UTF-8, exactly once) + `spans: [Span]` (8 bytes per token: `length: UInt16`, `typeCode: UInt8`, `identifierIndex: UInt32`) + `identifierTable: [String]` (interned, 1-based; `0` means none). All-`let`, so unconditionally `Sendable` with no lock and no CoW. Read it via `enumerateSpans(_:)`; `components` exists only as a compatibility view. Its `Codable` is columnar and **deliberately incompatible** with `SemanticString`'s.
- `AtomicComponent` (`Components/AnyComponent.swift`) — type-erased leaf (like `AnyView`). Holds `string: String` + `type: SemanticType` + `identifier: String?`. `AnyComponent` is a deprecated typealias kept for source compatibility.
- `SemanticType` (`SemanticType.swift`) — enum categorizing text: `.standard`, `.comment`, `.keyword`, `.variable`, `.numeric`, `.argument`, `.error`, `.other`, `.type(TypeKind, Context)`, `.member(Context)`, `.function(Context)`. `TypeKind` ∈ {`.enum`, `.struct`, `.class`, `.protocol`, `.other`}; `Context` ∈ {`.declaration`, `.name`}.
- `SemanticStringBuilder` (`SemanticStringBuilder.swift`) — result builder using the `buildPartialBlock` pattern. Accepts components, arrays, optionals, `Void`, `SemanticString`, and any `CustomStringConvertible` (auto-wrapped in `Standard`). Supports `if`/`else`, `for`, and `buildArray`.

### Component Categories

**Atomic** (conform to `AtomicSemanticComponent`): `Keyword`, `Variable`, `Numeric`, `Argument`, `Comment`, `Error`, `TypeName`, `TypeDeclaration`, `MemberName`, `MemberDeclaration`, `FunctionName`, `FunctionDeclaration`, `Standard`, `Space`, `BreakLine`, `Indent`.

**Composite** (implement `buildComponents()` directly — in `Components/`): `Group` (with `.separator(...)`), `Joined` (auto-filters empty items, supports prefix/suffix as strings or builder closures), `ForEach` / `ForEachIndexed`, `IfLet`, `DeclarationBlock`, `NestedDeclaration`, `BlockList` (with `.separatedByEmptyLine()`), `MemberList`.

**Structural:** `EmptyComponent`, `TupleComponent2`, `TupleComponent3`.

**Protocol conformances that aren't obvious from filenames:** `Optional<Wrapped>`, `Array<Element>`, and `Never` all conform to `SemanticStringComponent` when `Wrapped`/`Element` do — this is how the builder swallows nil and iterates arrays cleanly.

### Storage: Flat Atoms + Element Boundaries

`SemanticString.Storage` is a single representation:

- **`atoms: [AtomicComponent]`** — every atom, in order, typed, zero boxing. An `AtomicComponent` is 40 bytes, larger than the 24-byte existential inline buffer, so storing it as `any SemanticStringComponent` would cost a 40-byte container **plus** a 64-byte heap box per token.
- **`elementEndOffsets: [Int]?`** — element boundaries as end offsets; `nil` means 1:1 (every atom is its own element). Element granularity is semantic — `MemberList`-style containers treat one element as one row — so it is recorded as *data* instead of being implied by a retained component tree. Composites are flattened **eagerly** on append and never retained: `buildComponents()` takes no context, so the flattening can only ever be done once, and only its result and its boundary matter.
- **`cachedString: String?`** — the lazy concatenation, the storage's **only** shared-mutable state.

Streaming (`append(_:type:)` / `write(_:)`) keeps `elementEndOffsets == nil` and never allocates structure. The table is materialized by the first append whose element is not exactly one non-empty atom — or by `init(components: [AtomicComponent])` when the input contains empty atoms, whose element slots it keeps — at 8 bytes per element (versus 104 bytes per token for the old boxed element tree). A component that flattens to nothing — an appended `nil` optional, `EmptyComponent`, an empty composite — is a **complete no-op** on every append overload (sixth round): no atoms, no element slot, no boundary-table materialization, no string-cache drop. **Zero-length elements** (`ends[i] == ends[i-1]`) survive in exactly one place: `init(components: [AtomicComponent])`, which keeps one slot per input entry so the table mirrors the input array's shape. Either way the slot is container-layout bookkeeping only — no public measure observes it; `isEmpty` reports components.

**Materializing the table is one allocation of `previousAtomCount` `Int`s, and it is permanent — known, measured, and not yet fixed.** The planned fix (`implicitPrefixCount: Int` + `explicitEndOffsets: [Int]`, so the 1:1 prefix costs one integer instead of one per atom) is described at the end of `docs/SeventhReviewFixes.md`. `closeElement(appendedAtomCount:)` turns an implicit 1:1 table explicit with `Array(1 ... previousAtomCount)`, so a *single* composite append onto a long streamed string allocates 8 bytes per pre-existing atom in one shot (measured: 1M streamed tokens then one two-atom `Group` append adds a 7.6 MB table to 38 MB of atoms, +20%). The table never de-materializes, and every later copy-on-write copies it too — the same measurement shows one `+` copying 38.2 MB before the composite append and 45.8 MB after. The "streaming carries zero overhead" property above holds only for strings that *never* receive a non-1:1 append.

**Two invariants.** Break either and the same content starts comparing or rendering differently depending on how it was built:

1. **Granularity is the boundary table.** One appended component is one element, whatever its atom count — including third-party leaves whose `buildComponents()` returns several atoms. An append whose input renders nothing records no element at all, on every overload (sixth round).

   **The one place granularity does depend on static type: appending a `SemanticString`.** `append(_ semanticString: SemanticString)` splices *element-wise*, preserving the operand's own boundaries; the generic `append(_ component: some SemanticStringComponent)` recognises a `SemanticString` through `as?` and routes it to `appendSemanticStringElement`, which records it as **one** element. Overload resolution is static, so the same value takes different paths depending on the caller's static type — a generic or existential context sees only `some SemanticStringComponent`. Measured: a four-element `source` appended directly renders 6 rows in `MemberList(level: 1,)`, and the identical value appended inside `func f<Component: SemanticStringComponent>(_ x: Component, into t: inout SemanticString)` renders 3 — while the two results compare `==`. This is deliberate for the builder (every builder child must stay one element, or `MemberList { for row in rows { row } }` would lose its rows), but it means element granularity is **not** a property of the value alone. Do not document it as one.
2. **No zero-length atoms in `atoms`, ever, on any path.** `components` returns the array verbatim, so every write entry point drops empty atoms (`flatContents(droppingZeroLengthComponentsFrom:)` for hand-built arrays — which records a zero-length *element* slot per dropped atom, layout bookkeeping no public measure observes — the append funnel, eager composite flattening). Filtering on *read* instead would make `components` O(n) with an allocation. Zero-length *elements* are recorded; zero-length *atoms* are not. One observable consequence, pinned in `ThirdReviewRegressionTests`: container emptiness sees the *filtered* flattening, so a third-party leaf whose `buildComponents()` emits only empty atoms gets no row and no separator — the same treatment `Keyword("")` has always had, where `main` treated the two shapes differently.

**The element view.** `SemanticString.elements` returns `SemanticStringElements` — either one contents run (`atoms` + boundary table) or an array of independent strings, both zero-copy. An element's components are always a contiguous run of the flat array, so containers read them as `ArraySlice`s via `atoms(ofElementAt:)`: no scratch buffers, no per-item array materialization, no boxing. The slices keep the flat array's absolute indices (a `.strings` slice starts at 0 instead), so consume them via `isEmpty`/iteration/`append(contentsOf:)`, never literal positions. Performance is a trade, not a free win: rendering a container over `[SemanticString]` items and streaming appends are measurably faster than both `main` and the two-state design, but the *builder collection* path (`SemanticString { for row in rows { row } }` and every container `content:` closure) copies each row's atoms once at collection and again at render — measured ~1.4–1.7× `main`, which paid one copy by retaining boxed elements. Numbers in `docs/ThirdReviewFixes.md`.

**Cache locking:** the lazy `cachedString` fill is guarded by `CacheLockStripes`, a table of 256 platform locks indexed by mixed storage address. The concatenation runs *outside* the lock (racing readers may both compute; results are identical, first store wins). Everything else — contents, boundaries — is only mutated on uniquely-referenced storage (`makeUniqueForMutation()`, the single copy-on-write path, which copies contents and skips the cache) and needs no lock. `components` reads the storage array directly: no lock, no cache, no side effect on any value sharing the storage — which is also why `frozen()` and `isEmpty` cannot inflate anything, nested member strings included.

The hot `string` read costs one uncontended lock round trip (~4–5 ns) that `main`'s unlocked cache did not pay — `main`'s version was a data race, and the lock is the price of fixing it. Do not add an unlocked fast path for it.

Two traps the striped locks exist to avoid, both measured (8 threads x 50k transient strings, one cold fill each):

- **One shared lock serializes unrelated strings.** That is the workload this type is built for, and it cost 434.9 ms against 46.6 ms for no lock at all — concurrent was slower than serial.
- **Packed stripes trade lock contention for false sharing.** An `os_unfair_lock` is 4 bytes, so 32 of them share a cache line; threads locking *different* stripes still bounce the same line. Packed: 273 ms, indistinguishable from running the work on one thread. Hence `CacheLockStripes.stride = 128` — one cache line per stripe. Spaced, 256 stripes: 44.7 ms.

If you add stripes, keep the count a power of two (the index masks) and keep the stride at a cache line.

**The stripe index must be mixed in `UInt64`, not `UInt`.** The multiplier is a 64-bit constant, so writing the mix in `UInt` is a compile error on 32-bit targets — which means watchOS devices, and see the build section above for why nothing else catches it. Truncating the multiplier to fit is the trap, not the fix: `mixed >> 32` is then always zero, every address lands on stripe 0, and the table degrades into exactly the one shared lock measured at 434.9 ms. `ReviewFindingsRegressionTests.stripeIndicesSpreadForNarrowAddresses` pins the spread.

Writing a test that needs two specific storages to *share* a stripe: don't build many pairs and hope. The index is a multiplicative hash of the address, and multiplication is linear, so two storages allocated a fixed number of bytes apart always land a fixed stripe distance apart — either always colliding or never. Measured: 4096 identically-built nested pairs, zero collisions. Vary how much is allocated *between* the two storages instead, and collisions appear on a fixed period. (The collision-search deadlock test that used this technique was removed with the recursive locking path itself: computing `string` now touches exactly one storage and takes exactly one stripe, so there is no lock ordering left to guard. If a change reintroduces nested locking, bring the technique back with it.)

**File layout.** `SemanticString` is split by functional area so no single file carries the whole type: `SemanticString.swift` (storage plumbing, contents, initializers), `+Mutation` (identifier scopes, the append funnel), `+Transformation` (map / trim / slice / filter), `+Query` (prefix, suffix, containment), `+Composition` (`appending`, wrapping, conditionals, operators), `+Conformances` (`Codable` / `Hashable` / `TextOutputStream`). Storage internals live in `Storage/` (`SemanticStringStorage`, `SemanticStringElements`, `CacheLockStripes`) and the frozen form in `Frozen/` (type, `+Freezing`, `+TypeCodes`, `+Codable`). Put new API in the extension file for its area rather than growing the core file.

See `docs/FlatStorageRedesign.md` for the flat-storage structural redesign (note: its behavior-decision section on `isEmpty`/`ForEach` predates the fifth round and is superseded by `docs/FifthReviewFixes.md`), `docs/ThirdReviewFixes.md` for the post-redesign correctness fixes (hand-built element slots, frozen canonical equality, grapheme-aligned splitting, decoder ordering) and the honest builder-path performance accounting, `docs/FourthReviewFixes.md` for the two frozen consistency fixes (Codable round-trip idempotence for out-of-range identifier indices, and `==`/`hash` normalizing unknown type codes to `.other`), `docs/FifthReviewFixes.md` for the fifth-round fixes (component-count `isEmpty`, the byte-gated frozen `==` fast path, walk-free hashing, typed-diagnostic traps, scope-preserving `appending("")`, and the doc/test-infrastructure honesty pass), `docs/SixthReviewFixes.md` for the sixth-round fixes (zero-width appends as complete no-ops, frozen `==` undercover enforcement, CRLF-terminated bodies, invariant pin tests, release-mode test guard), `docs/SeventhReviewFixes.md` for the seventh round's four-question verification pass and the documentation-honesty fixes it landed (plus the code fixes it defers, listed at its end), `docs/FrozenSemanticString.md` for the frozen form, and `docs/TwoStateStorage.md` / `docs/StorageCorrectnessAndLockRework.md` for the superseded two-state design this replaced (kept as history; the mechanisms they describe are gone).

**Before acting on a review finding, check `docs/SettledFindings.md`.** It records every finding previously judged a deliberate divergence, a deliberate non-fix, or a false positive, together with the reasoning. A finding that matches a settled entry whose rationale still holds is skipped, not re-litigated — five of the seventh round's fifteen findings were re-reports of decisions already made. ### Design Patterns & Invariants

- **All public APIs are `@inlinable`** for performance. When adding public API, match this convention. Note that **no test guards allocation counts or run time** (`PerformanceRegressionTests.swift` is functional pins despite its name; `StressTests.swift` has coarse timing budgets only) — performance claims must be verified by hand with a release-mode comparison against `main`, and the measured numbers belong in `docs/`.
- **Flattening happens once, at append time.** A composite is expanded by `buildComponents()` when it is appended and its atoms land in storage; `SemanticString.components` is the storage array itself — no lazy expansion, no component cache, no lock. Only `string` is lazily computed and cached.
- **`SemanticType` ↔ `UInt8` codes are append-only, and written out per case.** `SemanticType.frozenTypeCode` (`Frozen/FrozenSemanticString+TypeCodes.swift`) is a storage/wire format: new cases — including new `TypeKind` cases — take `SemanticType.nextFreeFrozenTypeCode`, existing assignments are **never** renumbered, or previously encoded frozen strings decode with the wrong styling. The inverse `init?(frozenTypeCode:)` returns `nil` for unknown codes, and its callers — `enumerateSpans`, `components`, and `FrozenSemanticString`'s `==`/`hash` — resolve those to `.other` rather than crashing or comparing on the raw byte, so a snapshot carrying a future encoder's unknown code renders and compares equal to one carrying `.other`'s own code (`FourthReviewRegressionTests.frozenEqualityNormalizesUnknownTypeCodes`). Decoding likewise preserves an unknown code verbatim rather than rejecting it. The codes are spelled out one per case rather than derived arithmetically: the previous `8 + typeKindOffset * 2` form put the `.type` block's growth edge against `.member`'s fixed 18, so adding a sixth `TypeKind` would have compiled and silently collided — and spelling them out does **not** remove that edge (`.type(.other, .name)` = 17 still sits against `.member(.declaration)` = 18; the next free pair is 22). The guard that actually catches a colliding new case is `FrozenSemanticStringTests.typeCodeBijection`: it asserts pairwise-unique codes and exact total count over an explicit case list — `TypeKind`/`Context` combinations come from `allCases`, but `SemanticType`'s top-level cases have no `CaseIterable` (associated values) and are enumerated by hand, kept honest by a compile-time exhaustiveness canary (`assertCaseListIsExhaustive` in the same file: adding a top-level case breaks its `switch`, forcing the list and the count to be updated together). `ReviewFindingsRegressionTests` additionally pins that every assigned code stays below `nextFreeFrozenTypeCode`.
- **Span lengths are `UInt16`, and only *scalar* alignment is guaranteed at every boundary.** A token over 65535 UTF-8 bytes is split into consecutive spans with identical type and identifier, at grapheme cluster boundaries — a scalar-boundary split concatenates back fine but hands span consumers (styling, selection, `components`) a broken half-cluster, e.g. a ZWJ emoji cut in the middle; a single cluster that itself exceeds 65535 bytes degrades to scalar boundaries. Cluster alignment does **not** hold across tokens: adjacent tokens can split one `Character` (`Keyword("e")` + `Standard("\u{0301}")` freezes to two spans through the composed character), so consumers needing cluster-aligned runs must merge adjacent spans. A test comparing token counts one-by-one against `SemanticString.components` will still see long-token splits.
- **Empty strings are filtered at the atomic level** — `AtomicSemanticComponent.buildComponents()` returns `[]` for empty `string`, so composite components can assume their children produce no empty noise. Storage upholds the same rule at every write entry point; see invariant 2 above.
- **`isEmpty` means "has no components", O(1).** The emptiness measures coincide — `isEmpty` ⟺ `count == 0` ⟺ `first == nil` ⟺ `string.isEmpty` — and agree with `==`/`hash`/`Codable`, which compare components, so equal values agree on `isEmpty` however they were built (fifth round; supersedes the earlier element-count semantics). Appends that flatten to nothing are complete no-ops (sixth round); the zero-length element slots kept by the hand-built array initializers are container-layout bookkeeping that no public measure observes. `ForEach(_:separator:)` uses `isEmpty` per item and therefore skips items that render nothing, consistent with `Joined`/`Group` — a deliberate divergence from `main`, which emitted separators around empty items.
- **Identifier scopes stamp `append(_:type:)` / `write(_:type:)` only.** Component appends never stamp; a component that wants an identifier carries its own via `AtomicComponent(string:type:identifier:)`. An `appending` call that actually appends returns a fresh copy carrying no scopes; an `appending` call that appends nothing (`appending("")`) returns `self` unchanged, open scopes included, matching `main`'s early return (fifth round; a streaming writer that probes with empty input must not lose the scope it is writing under). The conditional combinators (`if(false)`, `suffixed(if: false)`, `wrapped(if: false)`, `ifLet(nil)`) likewise return `self` unchanged and keep open scopes.
- **The zero-allocation append path is opt-in via `PlainAtomicSemanticComponent`.** `append` has four component overloads: exact `AtomicComponent` (keeps `identifier`), `some PlainAtomicSemanticComponent` (statically resolved, reads `string` / `type` straight into the atom array, so `Keyword` / `Space` / `Indent` / `TypeName` never allocate), `some AtomicSemanticComponent` (goes through `buildComponents()`), and `some SemanticStringComponent` (flattens eagerly). Every overload that appends content records exactly one element — however many atoms a custom `buildComponents()` returns, they stay one element — and an append that flattens to nothing is a complete no-op on every overload (sixth round: no element slot, no boundary-table materialization, no string-cache drop). The one exception is an operand that is *itself* a `SemanticString`, whose granularity depends on which overload the caller's static type selects; see invariant 1 above.

  Conforming to `PlainAtomicSemanticComponent` **promises that `buildComponents()` is the inherited default**, because the fast path does not call it. Conform a leaf that overrides `buildComponents()` and its *content* diverges between `append` and a `@SemanticStringBuilder`, and `AtomicComponent`, which overrides it to carry `identifier` through, would silently lose that identifier. Debug builds assert the promise on every fast-path append (fifth round), but that assertion is a **development aid, not a guarantee**: `assert` is compiled out under `-O`, so a violating conformance ships the divergence in release with no diagnostic (verified: `append` renders `"x"` while the builder renders `"<x>"`, the two values compare `!=` and hash differently, exit code 0). It only fires at all if a debug test happens to stream that particular leaf. The assertion also is not free — it evaluates `buildComponents()` through an `@autoclosure`, allocating the very array the fast path exists to avoid, which in debug makes this "zero-allocation" overload the *slowest* append path (measured: 300k appends, 149.7 ms via `append(Keyword(_:))` against 73.2 ms via `append(_:type:)`), and because the overload is `@inlinable` a downstream Debug app linked against a Release `Semantic` pays it too. New library leaves go in `Components/PlainAtomicComponentConformances.swift`; leaves that customize `buildComponents()` stay on `AtomicSemanticComponent` alone and take the slightly slower correct path. A new *composite* must not accidentally satisfy `AtomicSemanticComponent`.
- **`Indent` uses 4 spaces per level.** `DeclarationBlock` and `MemberList` both compute their own indentation using this 4-space rule (see `Components/Block.swift`); keep new layout components consistent.
- **Pre-computed singletons in `CommonAtomicComponents`** (`Components/Other.swift`) — reuse `CommonAtomicComponents.space` / `.breakLine` in new composite components instead of allocating new `AtomicComponent` values each time.
- **Composite components own their own whitespace.** `NestedDeclaration` prepends a `BreakLine`; `MemberList` emits `BreakLine + indent` before each item plus a trailing `BreakLine`; `BlockList` emits a leading `BreakLine` before each item and a trailing one. When composing these, don't double-add newlines.
- **Most composite initializers come in sync + async variants** (e.g. `DeclarationBlock`, `NestedDeclaration`, `BlockList`, `MemberList`). The async form uses `@SemanticStringBuilder (…) async throws -> SemanticString`. Keep this pairing when adding new block-like components.
