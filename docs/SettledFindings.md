# 已裁决清单

评审中被判定为**有意偏离**、**有意不修**或**误报**的发现，连同理由记录在此。

**用法**：每次 code-review 先对照本清单。命中且理由仍成立的发现**直接跳过**，不再重走四问；若有新证据推翻当初的理由，则更新本条并重新裁决，不要静默重报。

新增裁决时记录：现象、裁决、理由、裁决轮次。理由必须写清「为什么当时这样决定」，否则下一轮无法判断它是否仍然成立。

---

## S1 · 零长原子在一切构造路径被丢弃

- **现象**：`SemanticString(components: [a, "", b]).count == 2`（非 3）；旧版本载荷里的零长组件解码后消失，重编码字节数随之改变，组件索引整体前移。
- **裁决**：**有意偏离 `main`**（第二轮拍板，第五、六轮复核维持）。
- **理由**：这是让 `Codable` 往返**永远幂等**的前提——编码输出里不可能出现空原子。保留空原子则需要在读取路径过滤，`components` 将退化为 O(n) 且带一次分配。跨版本影响已在 `README.md` 写明警告（含"组件索引须从解码后的值重新推导"）。
- **仍然成立**：是。

## S2 · 容器判空看过滤后的展平（`ForEach` 跳过空项）

- **现象**：`ForEach(["a", "", "b"], separator: ", ")` 在 `main` 上渲染 `"a, , b"`，本分支渲染 `"a, b"`；`SemanticString(Standard("")).isEmpty` 由 `false` 翻为 `true`。
- **裁决**：**有意偏离**（第三轮定为第二条有意偏离，第五轮由**用户拍板**将 `isEmpty` 定为组件计数，第六轮明确判定重复报告此项为**误报**）。
- **理由**：`main` 自身不自洽——`Keyword("")`（默认 `buildComponents()` 返回空）一直被跳过，而第三方组件返回单个空原子却渲染成整行空行，同一个"空白叶子"因实现细节行为分叉。统一为"展平为空即为空"后，`isEmpty` ⟺ `count == 0` ⟺ `first == nil` ⟺ `string.isEmpty` 全部重合，且与 `==`/`hash`/`Codable` 的比较基准一致。恢复 `main` 行为需要容器知道"过滤前是否为空"，等于重新引入两套表示。输出已由 `ThirdReviewRegressionTests` 钉住六个容器。
- **仍然成立**：是。

## S3 · builder 收集路径慢于 `main`

- **现象**：`SemanticString { … }` 与容器 `content:` 闭包的装配路径慢于 `main`（第三轮实测 1.4–1.7×，第七轮实测 1.24×）。
- **裁决**：**有意不修**（第三轮如实记账，第五轮复核维持）。
- **理由**：急切展平在 builder 收集时拷一次、容器渲染再拷一次，`main` 靠保留装箱元素只拷一次。消除它就是把"保留结构"请回来——正是第二轮重设计拆掉的东西，而那次重设计消灭的是一整类组合面缺陷（10 项同源缺陷）。作为交换，流式 append 快 2.7×、`+=` 快 4×、`[SemanticString]` 条目容器快于 `main`。
- **仍然成立**：是。第七轮实测倍率（1.24×）**低于**已记账区间，未恶化。

## S4 · `PlainAtomicSemanticComponent` 违约叶子在 release 下的内容分叉

- **现象**：违约实现（conform 了却又 override `buildComponents()`）经 `append` 与经 `@SemanticStringBuilder` 渲染出不同内容，两值 `!=` 且 hash 不同；release 下无任何诊断。
- **裁决**：**有意不修**（第六轮）。
- **理由**：该快路径的全部价值就是不调用 `buildComponents()`，无法免费加运行时校验；协议文档整段警告 + debug 断言兜底。
- **仍然成立**：是，**但第七轮修正了文档表述**——协议文档原称断言会使违约实现"在首个流式测试即失败而不会发布分叉"，与实现相反，已改为实话。**另注**：断言自身的 debug 性能代价（快路径反而最慢）尚未处理，属独立的待修项，不在本条裁决范围内。

## S5 · 组件展平时机由读取时提前到 append 时

- **现象**：读取可变外部状态的第三方 `buildComponents()` 被就地快照——先搭容器、后解析名字/地址的延迟解析模式渲染出过期文本（`main` 渲染新值，本分支渲染旧值）。
- **裁决**：**有意取舍**（第二轮重设计）。
- **理由**：`buildComponents()` 无参数、确定性，composite 在构建之后没有再利用价值；总工作量不变，改变的只是时机。换来的是读取路径完全无副作用——"发布/不发布组件缓存"这个无法沿协议传递的概念整个消失（它曾导致 `frozen()` 保护了自己的缓存却填满每个被 `MemberList` 持有的子串的缓存）。
- **仍然成立**：是。第七轮补上了 `README.md` 的使用者侧迁移说明（此前只写在 `docs/` 与 `AGENTS.md`）。

## S6 · 元素边界经 `Codable` 往返坍缩为 1:1

- **现象**：元素边界不参与 `==`/`hash`/`Codable`。`==` 相等且 hash 相同的两个值在 `MemberList` 渲染出不同行数；`Codable` 往返、`replacing { $0 }` 这类恒等变换同样改变行数而 `==` 不变。
- **裁决**：**已知未修，独立跟踪**（第六轮）。
- **理由**：`main` 上表现**完全相同**（第七轮双二进制复核确认：3 行 vs 4 行、往返后 4 行，两侧逐项一致），属基线固有而非本分支回归；修法涉及编码格式决策（边界入编码 vs 修改 README 承诺），不应混在存储重构里。
- **仍然成立**：是。**跟踪**：[#2](https://github.com/MxIris-Reverse-Engineering/swift-semantic-string/issues/2)（第七轮补建）。第六轮承诺"单开 issue 独立跟踪"但一直未建，在此之前本条的唯一记录是一份已归档为历史的文档里的一句话——承诺了跟踪就要真的建，否则等于没记。

## S7 · 畸形 frozen 值的 trap 时机取决于哈希碰撞

- **现象**：`hash(into:)` 按设计不走文本，`==` 慢路径走。于是一个畸形值（unchecked init 构造，违反覆盖/对齐/零长不变量）算 hash 安静、单独插入 `Set` 安静，但当另一个值与它哈希碰撞、迫使 `==` 进入 span 解析环时进程 trap。实测：文本同为 `"abc"`、span 数与 typeCode/identifierIndex 全同、仅字节长度分别为 103 与 104 的两个畸形值哈希相同，第一次 `insert` 成功，第二次 exit 133。同理 `count` / `isEmpty` 对畸形值仍报告畸形的槽数而不 trap。
- **裁决**：**有意不修**（第五轮决策，第八轮复核维持并补文档）。
- **理由**：畸形值只能由 public unchecked 初始化器手工构造（`frozen()` 与解码器都不可能产出），该初始化器的契约明确写了违反不变量会 trap，所以"崩"在契约内。让 trap 时机变确定只有两条路，都比问题本身更糟：unchecked init 加校验就不再 unchecked（O(n) 代价正是它存在的理由），`hash` 重新走文本则撤销第五轮实测的 -62% 哈希 / -65% `Set` 插入收益。
- **仍然成立**：是。**但第五轮的影响面写的是"畸形值的 `Set` 插入从崩溃变为安静成功"，只在不发生哈希桶碰撞时成立**——这一层当时未评估。待补：unchecked init 的文档目前只列了 `enumerateSpans` / `components` / `==` 解析路径三个 trap 点，读者据此会以为容器操作安全，需补明"`Set`/`Dictionary` 插入可能触发解析环"。见 [EighthReviewFindings.md](EighthReviewFindings.md) 第 2 条。

## S8 · `-Ounchecked` 下 unchecked init 的守卫全部消失

- **现象**：`FrozenSemanticString` 的不变量守卫全是 `precondition` 且位于 `@inlinable` 函数体内，所以客户端的优化模式决定它们存不存在。`-Ounchecked` 实测：零长 span 静默产出 `["a", "", "b"]`（第七轮刚修掉的缺陷等于不存在），畸形值在 `Set` 中静默判等，10 项 exit test 转红。
- **裁决**：**语言语义部分不修；测试部分待修**（第八轮）。
- **理由**：`-Ounchecked` 移除 `precondition` 是 Swift 的全局语义，不是本库的缺陷——同一模式下标准库自己的数组边界检查也全部消失，`Array` 越界同样是 UB。要求库在用户显式选择的"关掉所有检查"模式下仍守住不变量，等于要求它不遵守该模式。真正该修的是测试：10 项 exit test 在该模式下变红而不是跳过，属第六轮给 `assert` 项加 `#if DEBUG` 时的横向排查遗漏。项目文档里没有任何命令使用 `-Ounchecked`。
- **仍然成立**：是。待补：unchecked init 文档写明"这些 trap 在 `-Ounchecked` 下不存在，契约降级为纯 UB 契约"。

## S9 · frozen `==`/`hash` 按归一后的语义判等，不按原始字节

- **现象**：`typeCode: 200`（未知码）与 `typeCode: 7`（`.other` 自己的码）的两个快照相等、哈希相同、互相去重；`Set` 保留先插入的那一个，因此被持久化的编码字节取决于插入顺序。越界 `identifierIndex` 同理。
- **裁决**：**有意为之**（第四轮的修复，第八轮复核维持）。
- **理由**：归一前 `==`/`hash` 比较原始字节，而 `enumerateSpans` / `components` / 渲染全部把未知码归一为 `.other`——两个被**每一个读者**渲染成完全相同内容的值判不相等，`Set`/`Dictionary` 查找互相落空，与 `==` 自述的"比较渲染内容而非存储布局"直接矛盾。第四轮同时写明了迁移路径：需要按原始字节区分的调用方改比 `spans.map(\.typeCode)`。
- **仍然成立**：是，**但第八轮补记一个第四轮未评估的后果**：`nextFreeFrozenTypeCode` 现为 22，将来第一次把真实语义赋给某个旧载荷已携带的码位时，此前相等的两个解码快照会突然不等——`Set` 成员关系跨库版本变化，无解码错误也无编译错误。这是任何"未知码归一"方案的固有属性（改用显式 `.unknown(UInt8)` 会把第四轮修掉的问题原样请回来，两者不可兼得）。待补：`AGENTS.md` 的类型码章节需写明"给既有码位赋新语义会改变已发布快照之间的相等性"。

## S10 · "急切展平使冷内存差于 `main`"

- **现象**：有评审报告称，对于构建后保留但从不渲染的字符串，本分支的常驻内存比 `main` 高约 19%（127.2 MB vs 107.0 MB）。
- **裁决**：**误报**（第八轮，三组独立测量均无法复现）。
- **理由**：10,000 个保留字符串、`/usr/bin/time -l` 峰值常驻集，三种内容形状下本分支的冷内存都**不高于** `main`：85 叶子 66.0 vs 65.8 MB（持平）、217 叶子 128.7 vs 142.7 MB（低 9.8%）、217 原子包在单个 `Group` 里 129.5 vs 144.0 MB（低 10.1%）。第三组是刻意构造的最不利形状，本分支仍更省——因为 `main` 的叶子本身也是装箱的：`Group` 内部持有的 builder 结果在 `main` 上已是整个装箱元素数组（每元素 40 字节容器 + 64 字节堆盒），比本分支的 40 字节原子更贵。渲染场景两侧差距更大（257.1 vs 138.6 MB）。
- **仍然成立**：是。注意区分：**时间**方向的 builder 收集路径回归是真实且已记账的，见 [S3](#s3--builder-收集路径慢于-main)；**冷内存**方向不存在回归。再次收到此报告时先看本条。
