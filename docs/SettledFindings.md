# 已裁决清单

评审中被判定为**有意偏离**、**有意不修**或**误报**的发现，连同理由记录在此。

**用法**：每次 code-review 先对照本清单。命中且理由仍成立的发现**直接跳过**，不再重走四问；若有新证据推翻当初的理由，则更新本条并重新裁决，不要静默重报。

新增裁决时记录：现象、裁决、理由、裁决轮次。理由必须写清「为什么当时这样决定」，否则下一轮无法判断它是否仍然成立。

---

## S1 · 零长原子在一切构造路径被丢弃

- **现象**：`SemanticString(components: [a, "", b]).count == 2`（非 3）；旧版本载荷里的零长组件解码后消失，重编码字节数随之改变，组件索引整体前移。
- **裁决**：**有意偏离 `main`**（第二轮拍板，第五、六轮复核维持）。
- **理由**：这是让 `Codable` 往返**永远幂等**的前提——编码输出里不可能出现空原子。保留空原子则需要在读取路径过滤，`components` 将退化为 O(n) 且带一次分配。跨版本影响已在 `README.md` 写明警告（含"组件索引须从解码后的值重新推导"）。
- **仍然成立**：是。

## S2 · 容器判空看过滤后的展平（`ForEach` 跳过空项）

- **现象**：`ForEach(["a", "", "b"], separator: ", ")` 在 `main` 上渲染 `"a, , b"`，本分支渲染 `"a, b"`；`SemanticString(Standard("")).isEmpty` 由 `false` 翻为 `true`。
- **裁决**：**有意偏离**（第三轮定为第二条有意偏离，第五轮由**用户拍板**将 `isEmpty` 定为组件计数，第六轮明确判定重复报告此项为**误报**）。
- **理由**：`main` 自身不自洽——`Keyword("")`（默认 `buildComponents()` 返回空）一直被跳过，而第三方组件返回单个空原子却渲染成整行空行，同一个"空白叶子"因实现细节行为分叉。统一为"展平为空即为空"后，`isEmpty` ⟺ `count == 0` ⟺ `first == nil` ⟺ `string.isEmpty` 全部重合，且与 `==`/`hash`/`Codable` 的比较基准一致。恢复 `main` 行为需要容器知道"过滤前是否为空"，等于重新引入两套表示。输出已由 `ThirdReviewRegressionTests` 钉住六个容器。
- **仍然成立**：是。

## S3 · builder 收集路径慢于 `main`

- **现象**：`SemanticString { … }` 与容器 `content:` 闭包的装配路径慢于 `main`（第三轮实测 1.4–1.7×，第七轮实测 1.24×）。
- **裁决**：**有意不修**（第三轮如实记账，第五轮复核维持）。
- **理由**：急切展平在 builder 收集时拷一次、容器渲染再拷一次，`main` 靠保留装箱元素只拷一次。消除它就是把"保留结构"请回来——正是第二轮重设计拆掉的东西，而那次重设计消灭的是一整类组合面缺陷（10 项同源缺陷）。作为交换，流式 append 快 2.7×、`+=` 快 4×、`[SemanticString]` 条目容器快于 `main`。
- **仍然成立**：是。第七轮实测倍率（1.24×）**低于**已记账区间，未恶化。

## S4 · `PlainAtomicSemanticComponent` 违约叶子在 release 下的内容分叉

- **现象**：违约实现（conform 了却又 override `buildComponents()`）经 `append` 与经 `@SemanticStringBuilder` 渲染出不同内容，两值 `!=` 且 hash 不同；release 下无任何诊断。
- **裁决**：**有意不修**（第六轮）。
- **理由**：该快路径的全部价值就是不调用 `buildComponents()`，无法免费加运行时校验；协议文档整段警告 + debug 断言兜底。
- **仍然成立**：是，**但第七轮修正了文档表述**——协议文档原称断言会使违约实现"在首个流式测试即失败而不会发布分叉"，与实现相反，已改为实话。**另注**：断言自身的 debug 性能代价（快路径反而最慢）尚未处理，属独立的待修项，不在本条裁决范围内。

## S5 · 组件展平时机由读取时提前到 append 时

- **现象**：读取可变外部状态的第三方 `buildComponents()` 被就地快照——先搭容器、后解析名字/地址的延迟解析模式渲染出过期文本（`main` 渲染新值，本分支渲染旧值）。
- **裁决**：**有意取舍**（第二轮重设计）。
- **理由**：`buildComponents()` 无参数、确定性，composite 在构建之后没有再利用价值；总工作量不变，改变的只是时机。换来的是读取路径完全无副作用——"发布/不发布组件缓存"这个无法沿协议传递的概念整个消失（它曾导致 `frozen()` 保护了自己的缓存却填满每个被 `MemberList` 持有的子串的缓存）。
- **仍然成立**：是。第七轮补上了 `README.md` 的使用者侧迁移说明（此前只写在 `docs/` 与 `AGENTS.md`）。

## S6 · 元素边界经 `Codable` 往返坍缩为 1:1

- **现象**：元素边界不参与 `==`/`hash`/`Codable`。`==` 相等且 hash 相同的两个值在 `MemberList` 渲染出不同行数；`Codable` 往返、`replacing { $0 }` 这类恒等变换同样改变行数而 `==` 不变。
- **裁决**：**已知未修，独立跟踪**（第六轮）。
- **理由**：`main` 上表现**完全相同**（第七轮双二进制复核确认：3 行 vs 4 行、往返后 4 行，两侧逐项一致），属基线固有而非本分支回归；修法涉及编码格式决策（边界入编码 vs 修改 README 承诺），不应混在存储重构里。
- **仍然成立**：是。**跟踪**：[#2](https://github.com/MxIris-Reverse-Engineering/swift-semantic-string/issues/2)（第七轮补建）。第六轮承诺"单开 issue 独立跟踪"但一直未建，在此之前本条的唯一记录是一份已归档为历史的文档里的一句话——承诺了跟踪就要真的建，否则等于没记。
