# 定义区域：从父定义的打印结果里取出嵌套定义

- **状态**：已实现（分支 `feature/definition-regions`，尚未合入 `next`，尚未发版）
- **日期**：2026-10-01
- **使用方**：MachOSwiftSection 的 `marksNestedDefinitions`（它的提案 `draft-nested-definition-regions`）；RuntimeViewer 的 Find 语料

## 动机

RuntimeViewer 的 Find 给每个对象存一份打印好的 interface。嵌套类型会被打印两遍：父类型的打印里内联一遍，嵌套类型作为自己的对象又单独打印一遍。它的计时探针量出这部分约占打印时间的四成（Foundation 只打顶层 2.23 s、全打 3.72 s；SwiftUI 31.15 s 对 51.95 s）。改法是只打印父定义，从结果里把每个嵌套定义切出来，去掉嵌套带来的缩进后直接用。

今天切不出来：`NestedDeclaration` 把子定义的原子摊平进父定义，不留边界。只有打印器知道每个嵌套定义从哪个原子开始、到哪个原子结束，所以由它在输出时标出来；本库提供承载标记的方式、读回标记的表，以及切片和去缩进两个操作。

## 范围

- 新组件 `DefinitionRegion`：包住一个嵌套定义的打印结果，带一个身份字符串。
- 冻结后分离：`FrozenSemanticString.separatingDefinitionRegions()`，返回去掉标记的文本和 `DefinitionRegionTable`（每个区域的身份、UTF-8 范围、深度、直接外层区域）。
- 取出一个区域：`FrozenSemanticString.content(ofDefinitionRegion:)`。
- 按行去缩进：`FrozenSemanticString.removingIndentation(levels:)`。

不改动：`SemanticString` 的存储、`frozen()`、`FrozenSemanticString` 的存储布局与 `Codable` 格式，以及所有容器。不打标记的调用方看不到任何差别，容器也不多做任何判断。

## 关键设计与取舍

### 标记放在原子的 `identifier` 上，可见性标记始终在最外层

和可见性区域一样，标记写在原子的 `identifier` 里，不插入额外原子，理由见 [VisibilityRegions.md](VisibilityRegions.md)。编码是 `␆<身份…>␆<原 identifier>`，多个身份（外层在前）之间用 `␇` 分隔（U+0006、U+0007）。

一个原子同时带两种标记时，定义区域的编码放进可见性标记的「原 identifier」部分：`␁<条件>␁␆<身份>␆<原 identifier>`。这样做的原因是：容器和 `separatingVisibilityRegions()` 都靠第一个字符认出可见性标记，可见性标记留在最外层，它们一行都不用改，也察觉不到定义区域的存在。由此得到两条性质，测试都钉住了：

- 可见性区域包定义区域、定义区域包可见性区域，两种嵌套顺序得到的原子逐个相同。
- 两种分离可以按任意顺序做，得到的文本和两张表都相同。

否决的做法：把定义区域的编码放在最外层。那样容器会把带条件的成员当成无条件的（它只看第一个字符），投影就错了；要么就得规定调用方必须先分离定义区域、再分离可见性区域，把顺序约束推给每个调用方。

### 区域只覆盖内容本身

`NestedDeclaration` 在嵌套定义前面打的换行，以及容器打在它周围的任何东西，都属于外层文本——这些恰好是这个定义单独打印时没有的部分。所以定义区域不需要容器配合，这一点和可见性区域不同：可见性区域要求容器把成员的条件带到自己打的装饰上。

区域可以嵌套。分离时按 span 顺序维护一个「当前所在区域」的栈：相邻两个 span 的身份列表从外往里比，相同的前缀继续，不同处关闭旧区域、打开新区域。所以表里的区域按起点排序，外层区域排在它的内层区域前面。紧挨着的两个同身份区域读回来是一个，因为没有额外的边界信息可以把它们分开；MachOSwiftSection 用名字节点的 mangled name 做身份，同一个父定义里不会重复。

### 取出：在带标记的串上切，不在分离后的文本上切

`content(ofDefinitionRegion:)` 作用在带标记的冻结串上：切出区域的文本和 span，从每个原子上去掉该区域及其外层区域的身份，保留内层区域的身份和可见性标记，再按 `frozen()` 的方式（各 identifier 按 span 首次使用的顺序）重建 identifier 表。结果等于这个定义单独打印并冻结的值，缩进除外；调用方对它做两种分离，得到的文本和两张表与单独打印后分离出的完全一致。

必须重建表，因为 `separatingVisibilityRegions()` 按 identifier 表的顺序给条件编号：表里多出父定义的条目，或者顺序不同，切出来的可见性区域表就和单独打印的对不上。

否决的做法：在分离后的文本上切，同时切可见性区域表并平移偏移。那需要重新给条件编号、合并相邻区域、处理跨越切点的区域，等于把分离逻辑再写一遍，而且很容易在细节上与直接分离的结果分叉。

### 去缩进：按行，进到原子内部

每级 4 个空格，与 `Indent` 和各块组件一致。从文本开头和每个 `\n` 之后算起，每一行都必须以 N 级缩进开头，否则返回 `nil`；只有换行符的空行（`\n` 或 `\r\n`）和末尾的空行不动。去缩进按字节进行，跨原子边界、也进到原子内部：每行自带缩进的多行原子（例如逐 case 的 enum 布局注释）逐行去掉缩进。被去空的 span 整个删除，identifier 表同样按首次使用的顺序重建。

返回 `nil` 而不是 trap：父定义里某个嵌套定义不符合缩进约定时，调用方（RuntimeViewer）可以回退到单独打印它。

已知限制：超过 `UInt16.max` 字节的 token 会被切成多个 span，去缩进后切点随之平移，可能与直接冻结同样文本的切点不同；文本、类型和 identifier 仍然一致。

### 身份

身份是调用方给的字符串，本库不解释它的含义。它不能为空、不能含控制字符（编码保留了它们），违反时 trap，与可见性选项名的规则一致。MachOSwiftSection 在交给本库之前先检查，不合格的就不标记，让 RuntimeViewer 回退到单独打印。

## 影响面

- 纯增量 API，全部 `@inlinable`、`Sendable`，不引入任何依赖。
- 没打标记时：输出、行为和开销都不变，容器没有改动。
- 打标记的开销在调用方：每个被包住的原子多一次字符串拼接，嵌套深度为 k 的原子被逐层改写 k 次。

## 迁移注意事项

无需迁移。标记的编码是本库内部格式，调用方只通过 `DefinitionRegionTable` 和上面几个操作读写，不应自己解析 `identifier`。

## 验证

- `DefinitionRegionTests`（17 个测试）：编码往返、可见性标记保持在最外层、两种嵌套顺序得到相同原子、区域不改文本且保留元素结构、async 构造；分离还原无标记的打印并找出全部区域（含嵌套深度与外层索引）、两种分离任意顺序结果相同、同身份相邻区域合并；取出的嵌套定义去缩进后等于它的单独打印——文本、span、identifier、可见性区域表、定义区域表全部比较，覆盖多行原子、全部成员带条件的定义、带与不带可见性标记两种打印；去缩进的空行、失败、跨 span、多行原子、删空 span 与重建表；四个前提条件的 trap 用退出测试覆盖；README 里的示例原样跑一遍。
- 全部 432 个测试通过，watchOS `arm64_32` 编译通过。
